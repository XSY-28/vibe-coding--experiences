# vibe coding经验

用 AI 写代码时，可以随手翻一翻的经验清单。整理自蒋炎岩的《生成式软件工程》课程文字稿，以及社区维护的 [Karpathy 编码指南](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/README.zh.md)。

1. 开工前说清楚怎么验收。给什么输入，应该得到什么结果，哪些情况必须处理。别只留下一句“做得好用一点”。

2. 把影响方向的假设摆出来。一个需求有几种解释，就先说明差别；拿不准的数据结构、接口和业务规则，值得提前讨论。

3. 允许 AI 反驳你的方案。有更简单的办法，或者要求之间有冲突，就让它指出来，说明取舍。

4. 第一版只解决一个真实问题。选一件自己经常要做的事，让它从输入到输出完整跑通，实际用过再决定加什么。

5. 最不确定的部分先试。性能、兼容性、外部接口能否接通，尽早用小实验摸清，免得其他功能都写完才发现基础不成立。

6. 反馈尽量具体。页面哪里挤、哪个操作多余、预期结果与实际结果差在哪，直接指出来。参考图也比几个形容词管用。

7. 给 AI 当前用得上的材料。相关代码、现有范例、报错和约束放在一起；长期规则保持简短，临时要求留在当前任务里。

8. 先把职责和接口谈清楚，再拆任务并行做。大家都在猜接口时，增加 Agent 只会增加后面的协调工作。

9. 多个 Agent 各用各的工作目录。可以用 Git worktree 隔离修改；任务怎样接起来仍要事先约定，合并后再检查一次。

10. 对能检查、能撤销的实现，给 AI 一点独立工作的空间。人重点看那些会影响许多模块、改错后代价大的决定。

11. 能用简单实现解决，就先用简单实现。当前用不到的功能、通用框架和配置项，可以等具体需求出现再考虑。

12. 一次修改围绕一件事。修 bug 时顺手重构、升级依赖、调整全项目格式，出了问题会很难判断是哪一步引起的。

13. 在已有项目里，先读附近的代码。命名、接口和错误处理尽量沿用现有习惯；确实需要换做法，再解释原因。

14. 清理这次改动留下的废弃导入、变量和函数。原来就有的无关问题可以另记，别在没弄懂时一起删掉。

15. 留下能恢复的版本。完成一个有意义的步骤就保存 Git 检查点，提交说明写清改了什么、为什么改。文件存盘和提交到 Git 是两回事。

16. 修 bug 先复现，再检查修复是否有效。重构要确认原有行为还在；测试的预期结果应来自需求，别照着实现给自己出题。

17. 看实际产物。界面改了就打开，生成的文件就读一遍，需要扫码的二维码就真的扫。没验证的部分如实说明。

18. 多留意失败时的行为。空输入、重复操作、执行到一半出错以后怎么办，也属于需求。检查通过，只能说明检查覆盖的部分成立。

19. 看架构好不好，可以试着改一个需求。换输入格式、替换算法时，如果总要到处修改，就该重新考虑模块边界。

20. 越修越乱时，停下来检查概念和数据。状态由谁管理，结果依据什么算出，规则变化后旧数据怎么办，先把这些问题理顺。

21. 多次奏效的做法，再整理成 skill 或脚本。留下有用的判断标准和检查步骤；一次偶然失误，未必值得增加一条永久规则。

22. 流程跟着任务大小走。改错别字不用写一份计划；复杂任务则要说明每一步怎样判断做对了。

这些条目经过合并和改写，不是逐字摘录，也不表示每条都已经在独立项目中验证。课程部分依据官网目前公开的六讲文字稿，未逐段核对视频演示与口述。各条对应的材料见 [来源说明](SOURCES.md)。
